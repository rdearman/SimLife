# SimLife engine benchmark baseline — 2026-11-13

## Setup

- Release build of `simlife-bench`
- Linux 6.8.0-147-generic, x86_64
- AMD Ryzen 7 2700X (8 cores / 16 threads)
- One process per population size; one run per case
- Seed `20261113`, large 128×256 world, 100 simulated days
- Founders uniformly placed with speed 1, metabolism 2, fertility 0, herbivore diet, and 365-day lifespan
- Timed work includes simulation ticks, compact update construction, and state hashing. It excludes setup, PostgreSQL, HTTP, and browser work.
- Peak memory is Linux process `VmHWM`, including temporary state-hash serialization buffers.

No births occurred because benchmark founders have zero fertility. Population change therefore reflects survival under the current resource and metabolism rules. With this seed and setup, the 50k and 100k initial populations contract substantially over 100 days. This is an initial carrying-capacity observation, not evidence that those population levels are sustainable or that other genomes/seeds will behave the same way.

## Interpretation and limits

The largest tested population completed 100 ticks at about 15.4 ticks/second with about 42.0 MiB peak RSS in this local run. The cost rises with population because each server-style update hashes the world and copies organism state. The large map also has a fixed per-tick terrain/resource cost.

The 10,000-organism case was repeated with the same seed and inputs. Both runs ended with state hash `b200a2add394990dd8c459d85cdc29c98542657aa3e5beb248e81040e4e3a166`; timing and RSS varied slightly between runs.

These are single-run development-machine measurements. They have no warmup or repeated-sample statistics and do not include database checkpoint writes, concurrent worlds, or HTTP/WebSocket transport. Use them as a baseline for later optimization, not as production capacity claims. Re-run the documented commands on the target deployment hardware before setting supported workload limits.
